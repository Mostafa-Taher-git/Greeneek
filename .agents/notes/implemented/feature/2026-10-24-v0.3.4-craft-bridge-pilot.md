# Agent Note: Craft bridge pilot ships as a lazily-mounted gateway

Status: implemented

## Problem

The ArtCraft suite (PhotoCraft, PdfCraft, FigCraft, and siblings) exposes per-app CLIs and headless MCP servers, but every app ships its own ~10-18 meta-tools with per-app discovery, attach flags differ per app, several apps are early-alpha, and the live GUI control channel is unauthenticated upstream (their issue #480). Mounting static MCP clients per app would inflate every session's tool surface, break on partial installs, and — with an unauthenticated loopback port — attach to a channel that lets any local process drive the GUI.

## Decision

The v0.3.4 pilot ships the Craft bridge as a four-package seam (`packages/craft/{craft,craft-local,tool-craft}` + `packages/client/ui-craft`) with these rules:

- **Lazy gateway.** A session starts with exactly two model-facing tools: `craft_list_apps` (measured state per app) and `craft_open_app` (open headless, gated attach, or close). Opening an app mounts that app's curated tool bridge (names under the shared `mcp__<app>__<tool>` contract) and, only after its raw command registry matches a reviewed manifest hash, its recipe skill; a missing baseline or drift leaves the recipe disabled. Closing disposes both and releases the child process. `ToolBridgeOptions.toolFilter` in `gnk-mcp-client` drops filtered-out tools during the list phase, so a non-curated tool never holds a public name.
- **Manifests are data.** Each app's capability matrix (`manifests/*.json`) carries id/aliases, CLI stem, documented platforms, launch templates, attach gate, confined roots, min version, risky command classes, headless tool filter, artifact tool names and output patterns, per-fact provenance with an ISO date and a `verified` flag, and the row-level `verified` claim. Validation refuses unknown fields so a typo cannot silently weaken the posture, enforces the headless launch grammar at load (`{cli}` opens the template; the two roots and the token file appear), and refuses a row-level `verified: true` without a proven source entry. Unknown facts stay marked `unverified` until the real-app Windows E2E proves them.
- **Headless-first, attach hard-gated.** Only headless sessions open in the pilot: the attach path throws even for an attach-enabled manifest until the upstream authenticated channel ships. Live GUI attach is a per-app release gate, not a feature flag.
- **Security rules.** Read root is always the session workspace; write root is the job `out/` directory under it. Every path an app reports is confined against the write root — an escape fails the call. Each open mints a one-time per-launch control token; a loopback port without a token is never attached. Headless and connected launches require a `ready` discovery result, so an executable left behind by an unsupported, drifted, or failed installation is insufficient. Concurrency is capped by the validated `maxActiveApps` config (default 2). Child processes are owned by the session fiber and killed on teardown through `ctx.subprocess`.
- **CI without ArtCraft.** `CraftTransport` is the only app-wire surface the bridge sees; in-memory fakes cover discovery, open, call, and artifact paths, so Linux CI reaches the per-file coverage target with zero apps installed. One real smoke is reserved for the Windows desktop lane.
- **Desktop profile only, and not yet mounted.** The pilot lands as packages and tools without a preset or profile composition; the preview presets (Pixels Designer, Instructor) mount the gateway in a later wave. The browser Settings section falls back to the static pilot catalog reporting `unavailable` when no host-backed source is injected — the UI is honest about absence instead of guessing install state.

## Alternatives considered

**Per-app `craft_<app>_search/run` layer.** Rejected in the v0.3.4 plan consolidation: Craft already ships meta-tools with per-app discovery, so a hand-written search/run surface duplicates the vendor protocol and goes stale at each app release (v0.2→v0.15 churn).

**Nine static MCP client mounts at session start.** Rejected: ~160 tool schemas of turn cost on every session, it fails or loops on partial installs, and it cannot express the open/close lifecycle. The lazy gateway costs two schemas when idle.

**Screen-scraping or synthetic GUI input.** Rejected for 0.3.4: unauthenticated control channels make it unsafe, and it is unmaintainable across the suite's alpha churn.

**Silent install of missing apps.** Rejected: the launcher has no headless install CLI, and the product never installs software without an explicit user action; the settings section deep-links to the launcher/download page instead.

**Mount the gateway into the standard preset now.** Rejected: the pilot's manifests and links are `unverified` placeholders pending the real-app Windows E2E; shipping it in the default composition would expose an untested surface to every user.

## Consequences

- Idle sessions pay two tool schemas and spawn zero Rust processes; at most `maxActiveApps` Craft children exist per context, disposed with the session fiber.
- The suite beyond PhotoCraft and PdfCraft is manifest-stub territory: their integration is explicitly out of v0.3.4 scope, and the UI copy says "pilot".
- `verified: false` across both manifests means no release promise about real Craft behavior until the Windows smoke lands. Registry observations are process-local: cold-start status measures installation only, while a matching or drift-rejected open records the raw canonical hash used by later status reads.
- The bridge reuses the MCP tool-naming contract, so Craft app tools and real MCP servers share `publicToolName` and one conflict policy.
- Settings distinguishes unsupported versions, registry drift, and measurement failure from missing installations. Ordinary discovery errors become per-app `failed` rows without hiding cancellation or provider-selection failures.

## Verification

- `pnpm exec vitest run packages/craft packages/client/ui-craft packages/mcp/mcp-client` — 24 files / 361 tests pass with fake transports only (no ArtCraft installed, Linux-runnable).
- Manifest validation rejects unknown fields and non-pilot app ids; open-order security checks (attach gate, headless capability, roots, cap, token) each have a failing-path test in `packages/craft/craft/tests/service.spec.ts`.
