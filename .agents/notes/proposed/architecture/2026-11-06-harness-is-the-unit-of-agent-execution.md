# Agent Note: Harness is the unit of agent execution, and its capabilities are discovered

Status: proposed

## Problem

The owner ruled on 2026-11-06 that the shipped Fleet provider selector is conceptually wrong, not merely mislabelled. The user is meant to choose a **Harness** (Codex, Claude Code, OpenCode, KiloCode, Greeneek, Hermes, Agy, or a deployment-configured ACP agent). That Harness then determines the Models, reasoning Effort levels, Context capabilities and Permissions actually available inside it. `fork` and `spawn` are internal execution strategies, not user choices. Harmony and Melody are execution types independent of the Harness. Maestro remains the central orchestration authority and gains a Multi-Harness Debate mode. The previous round (S8-18b, S8-18c, S8-18e) shipped correct vocabulary and product names for provider rows, but it kept `fork` and `spawn` as user-selectable providers, so it is an engineering base to build on rather than the finished architecture.

The current tree was measured on 2026-11-06 at `f954198d`; every fact below is read from shipped source, not from a planning note.

**No Harness concept exists in code.** `SubagentProvider` in `packages/subagent/subagent/src/types.ts:319-365` has `name`, `capabilities`, `inheritsParentContext`, optional `agentRouteDefaults`, `start()`, and optional `prepareContinuable()`. `SubagentCapabilities` (`types.ts:86-93`) is exactly six start-time flags — `agentOptions`, `outputSchema`, `depthLimit`, `toolFilter`, `persona`, `agentPreset` — each asserted 1:1 against a request option by `assertCapabilities` (`packages/subagent/subagent/src/index.ts:624-641`). None describes models, effort levels, context strategies, permissions, connection state, or session lifecycle. The durable `SubagentDescriptorData` v4 (`src/descriptor.ts:72-90`) stores `agentProvider`/`agentModel`/`agentReasoningEffort`/`persona`/`toolFilter`/`agentPreset`/`cwd` with no capability metadata.

**Model and Effort are free text, not discovery.** `FleetFavoriteMember` (`packages/subagent/agent-team/src/fleet-settings.ts:42-60`) carries `model`, `reasoningEffort`, `context: 'fresh' | 'fork'`, `preset`, `readOnly`, `writeScopes`, `maxTokens`, and `timeoutMs`, but no `permissions` field. `packages/client/ui-agent-team/src/client/FleetSettingsSection.tsx:265-309` builds the provider `<select>` from live availability rows (good), but `context` is a static two-option enum and `preset`/`model`/`reasoningEffort` are plain `<input>` elements. Nothing checks that a typed model exists, that its effort level is supported, or that the selected provider can honor the request. `PROVIDER_NAME_KEYS` (`FleetSettingsSection.tsx:90-95`) hardcodes display names for four registry ids.

**External Harness metadata is discarded at the protocol boundary.** `packages/subagent/subagent-acp/src/run.ts:476-481` awaits `agent.initialize` with `clientCapabilities: {}` and never binds the result; `session.new` (`:483-491`) keeps only `sessionId`. `agentCapabilities`, advertised models, config options, and effort levels from the ACP InitializeResponse are dropped. There is no `supportedEffortLevels`, `supportedReasoningEfforts`, or `model/list` handling anywhere in the repository. The closest in-repo precedent is the **host** side: `packages/acp/acp/src/model-control.ts:144-219` builds Model and Reasoning-effort config options dynamically from `llm.listProviders()`, `llm.listModels()` and `resolveModelInfo()`, keeping model id, display name and description separate. `packages/subagent/tool-subagent/src/list-models.ts:86-113` publishes `list_subagent_models` for in-process children from the host LLM registry, filtered by a static `ModelSelectionPolicy.routes` allowlist. Neither negotiates with an external agent.

**Availability is registration truth, not capability truth.** `fleetProviderAvailability` (`fleet-settings.ts:322-347`) emits only `not-installed`, `one-shot` and `ready`, although `FleetProviderState` (`:18-23`) declares five states including `unauthenticated` and `temporarily-unavailable`. `admittedProviders()` is `ctx.subagents.list()` and `continuableProviders()` is the `prepareContinuable` subset (`packages/subagent/agent-team/src/index.ts:532-554`). Maestro knows provider names and that one boolean; `packages/subagent/tool-agent-team/src/index.ts:263-274,382-438` and the Maestro/Army presets carry no model, effort, permission, or connection facts. The owner's KiloCode zero-credit and Hermes rejected-key states measured on 2026-11-04 cannot be reported honestly through this vocabulary.

**Two decisions must not be broken.** [Fleets hold native agents and external CLI agents through one execution seam](2026-11-03-hybrid-fleets-use-the-subagent-provider-seam.md) establishes that native in-harness agents and external CLI agents share `SubagentProvider`, with eligibility derived from descriptor capability rather than a family tag; adding a parallel `AgentExecution` interface was explicitly rejected there. S8-18b/c/e fixes Harmony (persistent `fork` lane) and Melody (independent one-shot `spawn`) as user-facing names while keeping identifiers, persisted `mode` values, `spawnTeammate`, and the `team/member` schema untouched. Any Harness work must preserve both, and must not re-record recorded-session goldens from this Windows host.

## Proposal

Adopt the owner's seven standing decisions as architecture, and implement them by **extending the existing seam**, not by creating a framework beside it. The layering is: Greeneek UI (Harness / Model / Effort / Context / Permissions / Execution) → Harness Registry (discovery of registered Harnesses and named connections) → Harness Adapter (authentication and connections, session lifecycle, model and capability discovery, reasoning effort, context and permission declaration) → Normalized Execution Interface (`SubagentProvider` and its result contract) → Maestro / Fleet / Modes (orchestration and delegation).

1. **Harness is the unit of agent execution.** A Harness owns its own Models, Effort levels, Context strategies, Permissions, session lifecycle and connection state. A Provider name is a registry id, not a product identity; a Connection is a named authentication instance of a Harness, so `Claude Work` and `Claude Personal` are two connections of one Harness, not two Harnesses.
2. **Each Harness advertises its own capabilities.** The registry reads a `HarnessDescriptor` from each registered provider. Absent or unknown metadata is reported as unknown; it is never filled from a static catalog presented as live. An unsupported setting refuses loud with a named reason, continuing the `UNSUPPORTED_CAPABILITY` rule rather than accepting and ignoring.
3. **Model discovery is dynamic.** Where the protocol or CLI exposes it (`model/list`, Initialization Response, `provider list --json`, a curated catalog), Greeneek reads it at runtime, caches it with a drift hash, and keeps the real model id for execution while using display name and description for presentation. Where a Harness exposes no discovery surface, the UI says so and offers a declared manual id rather than a fabricated list. `Default` sends no override and leaves the Harness in control.
4. **Effort, Context and Permissions are capability-derived.** Effort levels are read per model (`supportedEffortLevels`, `supportedReasoningEfforts`, `defaultReasoningEffort`, or the ACP-declared equivalent), not assumed to be Low/Medium/High/Max. **Advanced Context Override (option C)** shows exactly what the Harness declares it can do: session forking, fresh context, additional context injection, context recovery, and resuming an old session. No setting promises behavior the Harness cannot perform.
5. **`fork` and `spawn` disappear from user choices and remain internal execution strategies.** They stay as identifiers, provider registrations and persisted values behind the Greeneek Harness Adapter. Harmony and Melody stay execution types independent of the Harness, selected per Fleet member.
6. **Greeneek is its own Harness.** The in-harness runtime gets an adapter that publishes its host LLM registry, effort levels and context strategies through the same descriptor, so a Fleet can mix Greeneek with external Harnesses without a special case. This reuses `packages/acp/acp/src/model-control.ts`'s dynamic option construction and `tool-subagent`'s `list_subagent_models` catalog instead of duplicating them.
7. **Maestro keeps and extends central authority.** Standard, Army, Maestro, Pixels Designer, Instructor and other modes are independent of Harnesses. Each Fleet member has its own execution profile (name, role, Harness, Connection, Model, Effort, Context, Permissions, Execution Type, timeout). Maestro can change a member's Harness or Model mid-conversation for new tasks without rebuilding the conversation or renaming the member, and a per-task override does not rewrite the saved Fleet without the user's consent. All of it happens in one chat, with Maestro routing only the context each agent needs — Planner output to Developer, Developer changes to Reviewer — rather than forwarding whole histories. The user may define a Fleet explicitly or ask Maestro to compose one.

**Multi-Harness Debate is a first-class orchestration mode.** Maestro is the moderator: it sets the question, runs the rounds, evaluates evidence and issues the final synthesis. Rounds are Independent Proposals (each Harness answers without seeing the others), Cross-Examination (each reviews the others' proposals and names weaknesses), Rebuttal, Evidence Review (code, tests, or references that support a claim), and Final Synthesis (agreements, disagreements, decision, confidence level). The user sets the round count, participants, and each participant's Harness, Model and Effort. Maestro chooses among **Consensus**, **Majority**, **Evidence-based Decision** (strongest evidence wins even when it is a minority position), and **No Consensus** (report the disagreement plainly); a majority is never treated as proof of a false claim. Variants are Adversarial Debate, Expert Panel, Red Team / Blue Team, Research Debate, Code Debate, Live Debate with messages visible in the same chat, and Debate History. Debate is **read-only toward the project by default**; implementing a recommendation needs explicit approval or delegation.

**Implementation increments, each with an enforcing consumer and a test.** No field is stored before its consumer exists — the shape this plan already rejected for `priority` and `default` fleet. H1: add `HarnessDescriptor` as an optional, additive field on `SubagentProvider` registration (registrations stay effects; `register()` keeps returning the disposer) with a gate test that every shipped provider advertises only capabilities it implements, and that a claim without an implementation is refused. H2: retain the ACP InitializeResponse in `subagent-acp/src/run.ts` and surface its advertised capabilities on the descriptor, with unit tests over a fake ACP child and a real-CLI e2e that self-skips with its reason printed when the executable is absent. H3: implement dynamic model and effort discovery per Harness, with `unknown` as a first-class result, id/display-name separation, a cache with a drift hash, and a refusal when a requested model or effort is not advertised. H4: replace the Fleet Settings provider selector with a Harness/Connection selector and render Model, Effort, Context and Permissions from the descriptor only; `Default` sends no override; `fork`/`spawn` leave the user-facing list while their identifiers survive; keep the three-locale parity, WCAG and logical-CSS gates green. H5: persist per-member execution profiles, separate saved Fleet settings from per-task overrides, and add Maestro's runtime reconfiguration plus context routing with a test that a one-task override does not mutate the saved favorite. H6: implement Maestro authority over every mode from one chat, including mixed-Harness parallel work and review of one agent's output by another. H7: implement Multi-Harness Debate with its five rounds, four decision modes, read-only default, history, and live messages in the same conversation. Every increment lands with focused tests, the relevant repository gates on the exact commit, and a ledger row in [the v0.3.9 master release plan](../process/2026-11-01-v0.3.9-master-release-plan.md).

**Sequencing constraint.** These increments follow the plan's actual phase order: Phase 0 green twice on one SHA, then CTC, then the release-engineering gates, and only then Phase 8. Model-facing text changes (presets, tool descriptions, the Team policy) must check the recorded-session snapshot path before landing, exactly as S8-18d did. Nothing here widens a v0.3.9 gate or waits on Phase 9's Browser AI Accounts; the three-concept separation of `ModelProvider`, `AgentProvider` and `BrowserAIProvider`, and the Phase 9 compliance constraint that no subscription OAuth token is extracted into a Greeneek-owned inference request, stay binding.

## Acceptance criteria

- A user creating a Task or adding a Fleet member selects a Harness, then sees only Models that Harness advertises, only Effort levels that Model supports, only Context overrides the Harness declares, and only Permissions it supports; `Default` sends no override. Selecting an unsupported value is refused by name, never silently ignored or replaced with a different Harness.
- `fork` and `spawn` appear in no user-facing selector, while their identifiers, persisted values, `spawnTeammate`, `TeamMemberMode`, and the `team/member` schema remain unchanged and Harmony/Melody remain execution types.
- Greeneek itself is a Harness in the same registry, with its host LLM registry published through the same descriptor, and one Fleet can contain a Greeneek member plus two external Harnesses with independent Models and Effort.
- One named Connection per authentication instance: two connections of the same Harness are distinct connections, not two Harnesses.
- Maestro changes a member's Harness or Model mid-conversation for subsequent tasks without rebuilding the chat or changing the member's identity; a per-task override leaves the saved favorite byte-identical; each agent receives only the context Maestro routes to it.
- A Multi-Harness Debate runs all five rounds with visible messages in the same chat, produces a final synthesis naming agreements, disagreements, evidence and confidence, supports all four decision modes, defaults to read-only, and requires explicit authorization before any recommendation is applied.
- Every new descriptor field has an enforcing consumer and a focused test; a provider that advertises a capability it cannot perform fails a gate. Mocked CLI coverage is never reported as real-CLI verification.
- `pnpm run test:docs`, `verify-generated-artifacts`, `verify-cordis-config`, the client i18n and logical-CSS gates, the focused unit suites, and `vitest --coverage` on the touched sources are green on the exact commit; recorded Web goldens are re-recorded only from the ubuntu lane when model-facing text moves.

## Risks

**Static catalogs drift.** A hand-written model or effort list becomes wrong on the next Harness release. Mitigation: discovery at runtime with a drift-hashed cache, `unknown` as an honest state, and no fabricated list; the manual-id path is explicitly labelled manual.

**Capability claims outrun implementations.** A descriptor field stored without a consumer recreates the stored-but-unenforced shape this plan already rejected for `priority`. Mitigation: each increment ships its consumer and a test in the same commit, plus the H1 gate that rejects a claim without an implementation.

**Protocol metadata is not uniform.** ACP, `model/list`, Initialization Response and `provider list --json` expose different fields, and some CLIs expose none. Mitigation: the normalized descriptor has explicit optional slots and an `unknown` state per slot; an adapter reports what it actually read, and the UI never assumes parity between Harnesses.

**Credential and compliance exposure.** Connection state must never appear in logs, cards, session history, chat, or PR comments; no CAPTCHA, MFA, anti-bot or access-control bypass; no private or undocumented endpoint used to imitate an official integration; provider terms re-verified at implementation time. Mitigation: carry only a credential reference in the descriptor, reuse the existing approval/permission model for consequential actions, and keep Debate read-only by default.

**Snapshot and golden churn.** Changing model-facing tool descriptions and preset prompts alters recorded sessions. Mitigation: check `snapshots/` before any such edit, re-record only from the POSIX lane, and never weaken an assertion to obtain green.

**Session catalog growth.** A Harness descriptor per provider adds model-facing metadata to every session. Mitigation: publish a compact summary in the session catalog and load full descriptors on demand through the existing skill/registry lookup pattern, measuring catalog size before and after H3.

## Alternatives considered

- **Clone PandaCode's provider architecture.** Rejected: the owner wants its Harness Registry, dynamic Model/Effort discovery, metadata separation, named connections and normalized protocol, but not its product; Greeneek keeps Maestro, Fleet, Harmony/Melody and its own `SubagentProvider` seam.
- **Hard-coded per-Harness model and effort lists.** Rejected: they go stale, cannot represent per-model effort support, and would present invented options as live.
- **Only rename the providers (the shipped S8-18e state).** Rejected by the owner: naming `fork` "Greeneek built-in" does not stop it being a user-facing provider choice, and leaves Model/Effort as free text. The shipped labels remain useful and are not undone.
- **A new parallel `AgentExecution` framework above `SubagentProvider`.** Rejected here and in [the hybrid fleet decision](2026-11-03-hybrid-fleets-use-the-subagent-provider-seam.md): it would duplicate capability advertisement, cancellation and structured-result contracts, then need its own consistency test against the seam it wraps.
- **Treat `fork` and `spawn` as Harnesses, or delete their code.** Rejected: they are internal execution strategies behind the Greeneek adapter. Removing the mechanisms would break durable lanes, persisting values, and the Tool/Mode contracts for no user-visible gain.
- **Assume every model supports Low/Medium/High effort, or decide Debate by majority vote.** Rejected: the first promises capability the Harness may not have; the second lets three agreeing agents certify a wrong fact. Effort is read from the Model, and Evidence-based Decision plus No Consensus are explicit outcomes.
