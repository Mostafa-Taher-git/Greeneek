# Agent Note: Desktop v0.4.4 session workspace controls

Status: proposed

## Problem

The desktop release candidate still exposes browser-oriented tray actions, while Greeneek's conversation header spreads session commands across several controls. The owner wants a desktop-first session workspace with three explicit toggles for thread details, the terminal drawer, and the right panel; Trajectory and session exports belong in thread details, and the live Harness fleet belongs below session lineage.

## Proposal

Finish the required `desktop-v0.3.9` plan in its recorded phase order, then ship this interface work as `desktop-v0.4.4`. Reuse Greeneek's existing session, Trajectory, export, layout, and Harness services; consolidate their presentation around three toggles and remove duplicate commands. Keep visible copy locale-owned and state in the existing client layout/session stores. The desktop tray keeps only actions that operate on the desktop window or application lifecycle.

The three controls are:

1. **Thread details** — opens the session details column with lineage, the live Harness fleet beneath lineage, Trajectory navigation, Copy Session as Markdown, and Download session log.
2. **Terminal drawer** — opens or closes the session terminal area and preserves its geometry and visibility according to the documented setting.
3. **Right panel** — opens or closes the right-side work panel without duplicating the details column.

Settings and shortcuts are limited to the state needed by these controls: panel visibility, panel sizing, and their keybindings. The settings page groups these options with the existing interface preferences and filters them through its current search model.

## Alternatives considered

### Why not copy every T3 setting?

Many T3 settings describe integrations and workflows Greeneek does not provide. Copying their names would create nonfunctional controls. Map the requested layout behaviors to Greeneek's current services and add only settings that drive shipped behavior.

### Why not add a second details or terminal state store?

`ui-layout` already owns panel geometry and visibility. A second store would allow the buttons, keyboard commands, and settings page to disagree about which panel is open.

### Why not keep browser launch in the tray?

The owner requested that Greeneek always open as a desktop app. A tray action that launches the web UI contradicts that entry behavior; external links and editor launching remain separate host capabilities.

## Acceptance criteria

- `desktop-v0.3.9` is completed or every remaining item is recorded in its existing ledger with the exact missing external input and evidence; no blocked owner input is represented as complete.
- The desktop UI has exactly three panel toggles with correct open/close state, focus labels, localization, keyboard behavior, and persisted settings.
- Thread details contains Trajectory, Copy Session as Markdown, Download session log, lineage, and the live Harness fleet in the requested order.
- Duplicate session actions appear in one intentional place, and the tray does not contain Open in Browser, Check for Updates, or Hide Window.
- Desktop unit and integration coverage exercises the real app entry; the shared client tests cover each panel state and export action.
- `pnpm run build`, `pnpm run typecheck`, `pnpm run lint`, `pnpm run doc-sync`, the relevant UI and desktop test lanes, and the desktop package smokes pass before a release tag is created.
- `desktop-v0.4.4` release notes and platform artifacts describe only features verified on the shipped desktop build.
