# Agent Note: desktop-v0.4.4 T3 parity — feature map and implementation plan

Status: proposed

## Problem

The desktop release candidate exposes browser-oriented tray actions and spreads the Session's own verbs across separate controls, while the requested desktop experience is a T3-shaped workspace: three independent panel toggles, one Thread Details column that owns the Session's transcript actions, one right panel that puts the Session lineage and the live Harness fleet in one hierarchy, and a desktop shell that never sends the user to a browser.

The reference is `https://github.com/pingdotgg/t3code` (MIT). Its UI lives in `apps/web/src`; the panels are `apps/web/src/components/chat/PanelLayoutControls.tsx`, `apps/web/src/components/chat/ThreadDetailsCard.tsx`, `apps/web/src/components/chat/ThreadDetailsPanel.tsx`, `apps/web/src/rightPanelStore.ts`, `apps/web/src/terminalUiStateStore.ts`, `apps/web/src/components/chat/ThreadRelationshipsControl.tsx`, `apps/web/src/components/chat/ChatRightPanel.tsx`, and `apps/web/src/components/RightPanelTabs.tsx`.

Three T3 facts shape this plan:

1. T3's "Previous agents" group is a *Session relationship* fact (the agents that ran under the thread), not a fleet roster fact.
2. T3 has **no** Trajectory view, **no** "Copy Session as Markdown", and **no** session-log download. Those three are Greeneek's own capabilities; T3 contributes the *placement* (Thread Details), not the feature.
3. T3's panel state is per-thread, persisted in `localStorage` (`t3code:right-panel-state:v2`, `t3code:terminal-state:v1`), with server state re-fetched over its WebSocket RPC layer.

## Proposal

Ship the desktop experience as four cooperating surfaces over one layout store: the Session header carries the three panel toggles, Thread Details carries the Session's transcript actions, the right panel carries the Session lineage, the Harness agents that ran, and the live Fleet, and the terminal drawer carries the Session's shell activity. The desktop shell stops offering browser-oriented actions, the panel preferences persist, and the Session Header keeps no duplicate menu.

## Acceptance criteria

1. The desktop layout has exactly three panel toggles, each opening and closing its own surface independently and in any combination, with the state persisted across a restart.
2. Thread Details carries *Trajectory*, *Copy Session as Markdown*, and *Download session log*; each acts on the current Session's real data, and the Session Header carries no duplicate menu for the same verbs.
3. The right panel shows the Session lineage, the Harness agents that ran under the Session, and the live Fleet, in that order.
4. The desktop tray offers Open Greeneek and Quit only, and the shell never sends the user to an external browser.
5. Every gate the repository owns is green: both typecheck faces, lint, the GUI suite, the desktop package tests, the documentation gates, the duplication gate, and the source-plane gate.
6. The live desktop application is operated and recorded: the three toggles, the three Thread Details actions, the terminal drawer, the right panel, the persisted panel state after a reload, the settings page, and the Arabic (RTL) layout.

## Alternatives considered

### Why not copy every T3 setting?

Many T3 settings describe integrations and workflows Greeneek does not provide: GitHub source control, device bridges, hosted browsers, side chats. Copying their names would create controls that change nothing. Every setting this release adds drives behavior Greeneek actually ships.

### Why not add an interactive terminal?

T3 embeds Ghostty (WebAssembly) and talks to a PTY over its WebSocket RPC. Greeneek's terminal sessions are host-side PTYs with no browser transport yet. The drawer therefore lists the Session's shell activity — the commands a turn ran and what they printed — and the gap is declared rather than filled with a dead terminal.

### Why not add a host git write path for *Commit & push*?

Writing to the user's repository needs an approval step and a host capability that does not exist yet. The read-only facts (branch, changes against the base) are already in the Workspace menu, and no dead entry is shipped in their place.

### Why not keep a second panel-visibility store?

`ui-layout` already owns the panel geometry and visibility. A second store would let the buttons, the keyboard commands, and the settings page disagree about which panel is open.

### Repairs found while adopting the implementation

- **Stray build output under `src/`.** A local build had left emitted `.js`/`.d.ts` files inside the package source trees; the source plane then resolved the *emitted* `src/client/index.js` beside the TypeScript source, so a spec that compares a registered component by identity saw two module instances of the same file. The stray output is removed and the gate is green again.
- **The layout store's persistence contract.** The store's unit account asserted that the panel geometry does *not* persist; the requirement is the opposite, so the account now proves the geometry survives a restart.
- **The test doubles that answered every slot.** The details-panel test doubles rendered the Tool body for *any* slot key, so the new Session-action slot produced a second Tool body. The doubles are now key-aware.

### The blank window, and the transcript copy that failed

Two defects the live desktop pass found, both invisible to the unit suites:

- **The blank window.** The desktop window loads the built web interface; when that build is missing or half-written, the page loads and paints nothing, and the shell — which only awaited the navigation — reported success. The window stayed blank with no message and no log. The shell now watches for the interface to paint, records the renderer's console output, its crashed renderers, and its preload failures in the same log the service writes, and shows the reason over the page with a retry when the interface never renders. The development launcher builds the web interface before the window opens when the build is absent, so the blank window cannot come from a missing build at all.
- **The transcript copy.** The Session export streams its archive, so each local file header carries no sizes — the real sizes follow the data in a descriptor, and the central directory at the end of the archive holds them. The copy trusted the local header, read an empty entry, and failed the inflate. The reader now walks the central directory and reads the data from the local header it points at; a regression test builds the same streamed archive and reads it back.

The copy now delivers the real transcript to the clipboard:

```
# ping

## User

ping

## Assistant

Pong! I'm here and ready. What would you like to work on?
```

Two defects fell out of the same migration, both invisible while the side panels were always mounted one-per-track:

- **A closed panel kept its controls in the tab order and the accessibility tree.** Thread Details and the right panel stay mounted at zero width, so their buttons were still focusable off-screen, and the Fleet panel's polite live region was the page's second `status` element even while the right panel was closed. Each side column now carries `inert` and `aria-hidden` exactly while its preference is closed; `inert` is applied first because a browser refuses to hide a subtree that still owns focus. The layout store's unit account proves both directions, and the browser suite's `image-display` and `lifecycle-chrome` status queries are unambiguous again.
- **A panel the user opened disappeared below the auto-collapse breakpoint.** The solver closes both side tracks to keep the center usable, which silently dropped a panel the user had asked for. A panel with an open preference and a solved zero track now leaves the grid flow and floats over the conversation (`data-overlay`), Thread Details first and the right panel last so it covers Thread Details when both are open. The unit account pins the overlay attributes, the document order, and the unchanged zero tracks.

- **The settings page opens** with its sections (eight section controls).
- **The Arabic (RTL) direction applies** (`dir="rtl"`).

One real defect surfaced only in the running application: the first implementation of the transcript copy read the export archive with `fflate`, whose Node entry the browser module table rejects (`require("module") missed the module table`), so the whole client failed to load ("Failed to load plugins"). The copy now reads the archive with the browser's own `DecompressionStream`, and the application loads.

## Risks

- The browser suite runs on Linux; a Windows host cannot regenerate its goldens faithfully (the file-manager labels and the shell tool name differ). The Linux refresh is the only source of truth.
- The terminal drawer is an activity view, not a PTY; the interactive terminal remains a declared gap.
- The fleet lineage and the agent history read the Session list projection; a Session whose children are not in the list shows an empty group rather than a stale one.
