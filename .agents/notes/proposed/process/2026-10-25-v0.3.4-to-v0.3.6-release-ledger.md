# Agent Note: v0.3.4 to v0.3.6 release ledger with per-requirement evidence

Status: proposed

## Problem

Plans, notes, and earlier summaries state intent, and each session that reads one inherits its claims as facts. The v0.3.4 plan plus the owner's release notes describe work spanning three releases, and parts of it are shipped, parts half-shipped, and parts absent, with no single place that ties each requirement to evidence an auditor can re-run. Without that, a session can report a milestone complete because a note said so, and a release can be tagged over an unverified claim.

## Proposal

Keep one ledger in the repository, updated after every wave, that labels each requirement DONE-VERIFIED, IMPLEMENTED-UNVERIFIED, PARTIAL, NOT STARTED, or BLOCKED, names the evidence (command run with its result, file path, or commit), and states the work remaining. This note seeds that ledger with the state established on 2026-10-25; the owner's issue #86 remains the external tracker and must be reconciled to it.

Baseline: work continues from `main @ 625a9ba5` — the Army browser surfaces, preset, and gate hygiene (`3a501389`, `f143e73d`, `f857d6bd`, `625a9ba5`, `5348b38f`) — with the CI pins on `fix/army-roster-catalog-pins @ 2309f484`. The plan's `c66636d8` baseline is historical, not a reset target.

- Desktop dev launch: an editor shell that exports `ELECTRON_RUN_AS_NODE` (VS Code and its derivatives set it for every child process) makes `electron .` run the Electron binary as bare Node. In that mode `import { app } from 'electron'` links against an empty built-in stub, and `require('electron')` returns the npm install stub's binary-path string, so `apps/desktop/src/main.js` never reaches `app.setName`. `pnpm --filter @greeneek/desktop run start` now runs `scripts/launch.mjs`, which clears the variable before spawning the installed Electron binary; `src/main.js` keeps its ESM named imports because they link under the real main process. `apps/desktop/test/launch.test.js` covers the sanitized launch, the unsanitized refusal, and the environment copy.

### Blockers that constrain every remaining claim

- `gh` is unauthenticated here, so no pull request can be opened for the fix branch and issue #86 cannot be updated; an unauthenticated Actions log download returns 404, so CI is read from check-run summaries only.
- No `GREENEEK_API_KEY` and no root `.env`: every live model flow, `test:e2e`, `test:snapshot:record`, and the Web golden refresh is NOT RUN.
- Replay lanes cannot run on this Windows host: `apps/web/tests/scaffold.ts` substitutes a `C:\…` workspace root into fixture JSON (34 parse failures, 44 Web suites) and `test:snapshot` compares against recorded POSIX paths (92 ACP and SDK cases). `docs/testing.md` now names the supported platforms.

## Decisions taken without further asking (2026-10-25)

The owner directed the remaining choices be made rather than raised. Recorded here with their reasons, and reversible by a later owner instruction:

- **Arabic ships as a built-in third locale**, not an out-of-band language pack. The request is "add the Arabic language like the 中文 and English", and `addLanguage()` exists for embedders, not for shipped product vocabulary; a language pack would leave every `Record<BuiltInLocaleId, …>` registration and the parity sweep proving only two languages.
- **Numerals are Western Arabic digits** (`123`), matching the digits every existing formatter, token count, cost figure, and English/Chinese string already produces, and keeping `Intl` number formatting aligned with the code that already pins locale-independent numerals. Eastern Arabic numerals would require revisiting each formatter and re-record the numeric Web goldens for no functional gain.
- **The UI opens by browser detection, unchanged in rule**: an Arabic-tagged browser gets Arabic, otherwise the stored preference wins, and English and Chinese behavior and their goldens stay as they are. No Arabic default is forced on this host, so the 15 English `snapshots/web/*/ui.expected.md` files are not re-recorded by the locale's arrival.
- **Milestone order stands as v0.3.4 → v0.3.5 → v0.3.6**, with Maestro G1 before Arabic and the Dashboard, because the Dashboard's most-used-CLI row and per-lane cost need Maestro's lanes to exist.
- **Live model flows stay recorded as BLOCKED, not worked around**: no credential exists in this environment and none will be invented, borrowed, or substituted with a mock result presented as a live run.

### M4 prerequisite proof (read from source, 2026-10-25)

Maestro's per-lane preset choice is implementable without touching the preset engine. A standing mount is one composition per preset id (`packages/preset/agent-presets/src/index.ts:775` `standingKeyFor`, `:781` `ensureStanding`, `:858` `StandingMount`), agents join it by scope parentage (`:459`), and `AgentSetup` already permits an async setup (`packages/core/agent/src/index.ts:60-63`, awaited before publication at `:105-120`). So a lane pre-warms with `await ctx.agentPresets.standingKeyFor(lanePreset)` before `agents.create`, then joins that scope inside the async setup. Today a subagent child inherits the parent's standing generation at `packages/subagent/subagent/src/child-agent.ts:204`, and the minimal contract change is `agentPreset` on `SubagentStartRequest` plus `SubagentCapabilities` and `ChildComposition`, with the lane join *replacing* that line rather than following it: `bindScopeParent` throws `scope key is already bound to a parent` on a double bind (`packages/core/scope/src/index.ts:72-75`). `childSessionMeta` (`child-agent.ts:138-156`) must then stamp the lane's preset id, not `composedPreset(parent.ctx)`, because a preset edited mid-flight resolves a newer generation. `SessionHeader.agentPreset` already exists (`packages/core/session/src/types.ts:129`) and is optional, so no `SESSION_FORMAT_VERSION` bump and no SDK regeneration follows. Unsupported-option behavior is a real gate: `packages/subagent/subagent/src/index.ts:631-635` throws `UNSUPPORTED_CAPABILITY`, and `NO_START_CAPABILITIES` (`out-of-process.ts:57-63`) is what codex, claude-code, and gnk-sdk advertise today.

The five promoted Agent Teams packages hold the durable pieces Maestro needs and none of them carries a preset or model per member: `TeamMemberSnapshot` records provider plus fresh/fork only (`packages/subagent/agent-team/src/types.ts:48-56`), roster spawn calls `startContinuable` with no preset slot (`roster.ts:246-300`), CAS is `revision` + `expectedRevision` (`types.ts:70-96`), and the README admits a flat roster with no nested team (`README.md:189-198`).

## Alternatives considered

**Issue #86 as the only tracker.** Rejected: it is external to the checkout, so a session cannot read it without `gh` authentication, and its text cannot be diffed alongside the commit that changes a requirement's status.

**Editing `docs/plan-v0.3.4.md` to record progress.** Rejected: the plan is the accepted-decision record, and marking requirements done there turns a plan into an apparent verification report whenever the claim outruns the evidence.

**One `implemented/` Agent Note per milestone.** Rejected: that lifecycle asserts finished work, so a half-delivered requirement would be recorded as complete; the ledger keeps the labels that distinguish verified from merely shipped.

## Acceptance criteria

- The ledger names an evidence line per requirement, and any claim without one carries IMPLEMENTED-UNVERIFIED or worse.
- v0.3.4 reaches: M0 pins green in CI on the exact commit, M1 contrast checks executable and dark block byte-identical, PTC migration measured before and after, Craft pilot provenance filled and one real smoke run or marked NOT RUN with the command, Army live E2E including budget kill and narrow-width stop, Maestro G1 gate met.
- Each release gate re-runs the applicable verification set from `docs/testing.md` on the exact pushed commit; a tag follows owner approval of the version and tag scheme.

## Risks

- Unverified claims are the dominant risk: the theme and Craft rows already read as shipped while their proof steps are absent, so a session trusting them can tag a release over them.
- The Windows replay gap hides real regressions behind environmental failures until the lane runs on Linux; only the CI pass settles it.
- Ledger drift: an unstale ledger misleads worse than none, so each wave must update it in the same commit as its change.
