## Reading the checkboxes (contract for the executing model)

A box is checked **only** when all five are true:

1. The implementation exists in the shipping path.
2. Focused tests cover the behavior and its failure modes.
3. The relevant repository gate passes on the exact commit.
4. User-visible or artifact-level evidence exists where the claim is user-visible.
5. The Execution ledger (end of this file) names the command, result, artifact hash, or file that proves it.

A mock presented as live is not done. A skipped test counted as green is not done. A box whose proof is blocked gets a `BLOCKED:` note naming the missing input — never a tick. Every item carries an ID (`S1-03` style) so the ledger can reference it without quoting prose.

# Mission: Transform Maestro into a Full Multi-Agent Orchestration System

I want to transform **Maestro Mode** into the central intelligence and orchestration layer of this application.

Maestro must have the ability to control, coordinate, and delegate work to all other available AI modes and supported CLI-based coding agents.

The goal is to build something significantly more capable than a traditional AI chat with a few agents. I want a genuinely intelligent multi-agent system where multiple agents can work simultaneously, each with its own CLI, model, reasoning effort, configuration, responsibilities, and execution context.

Use this repository as a major architectural and functional reference:

[https://github.com/amElnagdy/delegate-skills](https://github.com/amElnagdy/delegate-skills)

Study the entire repository, especially:

- Individual delegate skills and supported CLI integrations.

- `delegate-setup`.

- Fleet and lane configuration.

- CLI discovery and capability detection.

- Model, effort, and variant configuration.

- Task delegation and execution.

- Structured execution results.

- Session management and resuming.

- Parallel task queues.

- Execution monitoring.

- Diff review and integration.

- Error handling and recovery.


Understand how the existing implementation works before designing ours.

Important: Do not simply copy this project or install its skills and call the task complete. Use its ideas and implementation patterns as a starting point. Design a more unified, intelligent, extensible, user-friendly, and performant system.

Respect its MIT license and preserve applicable attribution if reusing code.

## 2. Maestro: The Central Orchestrator

Maestro must become the primary manager of every other AI mode.

Instead of simply responding to the user's request itself, Maestro should be able to:

1. Understand the user's objective.

2. Analyze the complexity of the request.

3. Break the objective into smaller, independent tasks.

4. Determine which tasks can run simultaneously.

5. Select the most appropriate available modes and CLI agents.

6. Assign each agent a specific role and task.

7. Configure its CLI, model, reasoning effort, and other supported settings.

8. Execute tasks concurrently whenever possible.

9. Monitor every agent's progress.

10. Evaluate the results.

11. Identify conflicting, incomplete, or incorrect results.

12. Coordinate additional work when necessary.

13. Combine the results into one coherent final outcome.

14. Report what was accomplished, what failed, and what requires attention.


Maestro must be able to delegate to ALL available modes, not just a predefined selection.

It should discover the available modes and their capabilities dynamically through a central agent/mode registry.

Examples of potential responsibilities:

- Planning and architecture.

- Research and investigation.

- Software development.

- Frontend and UI development.

- Backend development.

- Debugging.

- Code review.

- Testing and QA.

- Documentation.

- Performance optimization.

- Security analysis.


These are examples, not restrictions. Use the actual capabilities available in the application.

### Maestro must retain central authority.

Other modes should execute their assigned responsibilities, while Maestro remains responsible for:

- Task allocation.

- Execution coordination.

- Priorities.

- Dependencies.

- Progress monitoring.

- Agent communication.

- Conflict resolution.

- Result evaluation.

- Final integration.


Maestro should be able to give agents additional instructions, revise their assignments, stop unnecessary work, and request corrections.

## 3. Intelligent Parallel Execution

This is one of the most important requirements.

I don't want Maestro to execute everything sequentially when multiple agents could work at the same time.

For example, when I request:

"Analyze this project, identify problems, improve its architecture, implement missing features, improve the UI, and test everything."

Maestro could create a task plan similar to:

|Agent|Responsibility|Assignment|
|---|---|---|
|Agent 1|Architecture|Analyze the existing architecture and identify structural problems.|
|Agent 2|Code Review|Investigate bugs, technical debt, and potential improvements.|
|Agent 3|UI/UX|Analyze the interface and propose improvements.|
|Agent 4|Backend|Analyze backend functionality and identify implementation requirements.|
|Agent 5|QA|Analyze existing tests and prepare a testing strategy.|

These agents should begin working concurrently when their assignments are independent.

Maestro should then coordinate their findings and create subsequent tasks based on the results.

### Execution requirements

Implement:

- Parallel task execution.

- Task dependency graphs.

- Dynamic task scheduling.

- Configurable maximum concurrency.

- Agent availability detection.

- Resource-aware scheduling.

- Priority management.

- Task cancellation.

- Task retry and reassignment.

- Timeout management.

- Automatic recovery from recoverable failures.

- Dependency-aware execution.

- Incremental result collection.


Do not create parallel execution artificially. Agents must actually execute as independent processes or supported independent agent sessions.

For coding tasks, use isolated workspaces or Git worktrees where appropriate. Prevent multiple agents from accidentally overwriting each other's changes.

Maestro must understand which tasks can safely run together and which tasks must wait for other tasks to finish.

For example, implementation should generally happen after the relevant architectural decisions are established. Integration testing should run against the integrated result, not an arbitrary unfinished workspace.

## 4. Fleet Management and Custom Configurations

I want users to be able to create their own agent fleets.

A fleet represents a reusable collection of agents and their configurations for a particular type of work.

Users must be able to configure fleets from Settings or directly through natural-language instructions to Maestro.

### Example: Settings → Agent Fleets

Allow users to:

- Create a fleet.

- Rename a fleet.

- Delete a fleet.

- Duplicate a fleet.

- Edit its agents.

- Enable or disable agents.

## Phase 9 — Browser AI Accounts (owner-approved 2026-11-03; future milestone, not a v0.3.9 gate)

**Decision history, kept so nobody re-litigates it:** the owner first asked for an account-connection feature, then asked to park it, then issued a final decision that **supersedes both** — "Browser-based AI Accounts with Manual Conversations + Authorized Maestro & Modes Browser Interaction is APPROVED." It is approved product direction, recorded here as a properly scoped feature, and the owner directed that it must not be archived or re-parked, nor reconfirmed. It stays out of the v0.3.9 release gates: no v0.3.9 item may wait on it, and nothing here may be shipped by widening an existing gate.

Approved experience, two independently declared capabilities per provider:

**A. Manual conversation.** Each provider's official site opens inside Greeneek's own browser surface — not an external link-out and not an API key — where the user signs in through the provider's normal flow, including Free accounts, uses the site's own features, and keeps that session across restarts where the browser supports persistence.

**B. Authorized browser interaction.** Maestro and permitted Modes navigate, type, submit, and read visible responses in a connected session **only where that provider's current terms and the technical reality allow it**, behind an explicit capability declaration and Greeneek's existing approval/permission model for sensitive or externally consequential actions. Manual interaction stays available when automation is not.

Logging a provider in does **not** itself authorize automation. Before any provider's automation is built, its current official terms, policies, and technical restrictions are researched and the result recorded as a per-provider capability matrix; where automation is not permitted or not reliable, Greeneek ships Manual Mode and reports the exact limitation rather than approximating it. Never bypass CAPTCHA, MFA, anti-bot or access controls; never drive private or undocumented endpoints to imitate an official integration; never present unsupported capability as working.

### The distinction this feature rests on

**ModelProvider** — direct model inference. Today: `SubagentProvider` is *not* this; the inference seam is `packages/llm/llm`'s adapter registry (its absence answers `no adapter registered for provider "…"`), the upstream route catalog in `packages/llm/llm-pi-ai/src/catalog.ts` (which already lists `openrouter`), and the Greeneek adapter in `packages/llm/llm-greeneek`. Secrets live in `packages/credentials/credentials-local`; approvals in `packages/credentials/authorization`; the user surface is the Models settings section plus the first-run credential step.

**AgentProvider** — CLI or in-harness agent execution, where the *vendor's own product* authenticates. Today: `packages/subagent/subagent-claude-code`, `subagent-codex`, `subagent-acp`, `subagent-gnk-sdk`, and the in-process providers, all registered through `ctx.subagents.registerProvider()` and capability-gated by `SubagentProvider.capabilities` / `prepareContinuable`.

A connection is therefore one of two kinds, and the Settings UI must say which, because what "connected" proves differs: a ModelProvider connection authorizes Greeneek to call an endpoint; an AgentProvider connection authorizes Maestro to delegate to a program the user installed and signed into.

### Compliance constraint, verified 2026-11-03 (this is a hard requirement, not a preference)

- **Anthropic** — its published Claude Code legal/compliance guidance states Anthropic does not permit third-party developers to offer Claude.ai login in their own applications or to route requests through Free, Pro, Max, or Ultra subscription plans; OAuth tokens are restricted to first-party surfaces (code.claude.com/docs/en/legal-and-compliance; reporting of the change 2026-02 and 2026-04).
- **Google** — explicitly prohibits third-party tools from using Gemini CLI / Antigravity product OAuth to reach the backend services powering those products (reported 2026-09-18); the Gemini API authenticates with API keys (ai.google.dev/gemini-api/docs/api-key).
- **OpenAI** — the public API authenticates with API keys; ChatGPT OAuth exists for Codex-specific services through OpenAI's own client, and OpenAI has extended Codex seats across paid ChatGPT plans (developers.openai.com; OpenAI Services Agreement 2025-12-01).

**Three concepts, kept separate.** `ModelProvider` (API-based inference), `AgentProvider` (native and external agent execution through a vendor's own CLI), and `BrowserAIProvider` (an authenticated browser session for manual use and, where authorized, automation). A browser-account session is never merged into the inference or agent-execution registries, and a ModelProvider connection is never a precondition for Manual Mode.

**What the findings settle and what they do not.** They settle that Greeneek must not extract a provider's subscription token into its own HTTP client to imitate an official integration: the inference path stays key-based, and subscription-backed *agent execution* goes through the vendor's own CLI, which is already how `subagent-claude-code` / `subagent-codex` work. They do **not** by themselves decide Manual Mode — a user signing in inside Greeneek's own isolated browser profile is a different act from a third party calling a subscription backend — so each provider's embedded-browser and automation permission is researched and recorded separately in the capability matrix before any part B ships. Where the answer is no, Manual Mode only, with the exact limitation reported. Any change here re-verifies current terms rather than trusting this row.

### Scope

- **AC-01** Connection records: a typed connection kind (`model-provider` | `agent-provider`), vendor, credential reference (never the secret itself), display label, enabled flag, and last-verified status with reason, persisted through the existing `credentials-local` store and projected to Settings.
- **AC-02** Verification without spend: each connection has a probe that answers `ready` / `unauthenticated` / `not-installed` / `unsupported-version` / `temporarily-unavailable` from registry and configuration facts, matching the vocabulary `fleetProviderAvailability` already publishes; no probe may issue a paid or state-changing call.
- **AC-03** Model availability, not model invention: an authorized ModelProvider connection contributes its routable models to the same catalog the Models section already renders; Maestro and native modes select through the existing route resolution. No parallel catalog.
- **AC-04** Agent availability: an AgentProvider connection appears in the fleet member provider picker only when `ctx.subagents` registers it, and only with the capabilities its descriptor advertises — the rule the hybrid decision already enforces for fleets.
- **AC-05** Connection UI: one Settings section listing both kinds with the distinction stated, add/verify/disable/delete, and the reason for every non-ready state. Product copy through the locale dictionaries in all three languages, as `verify-client-ui-i18n` requires.
- **AC-06** Security: secrets never in logs, cards, session history, or chat; per-connection authority stays inside the existing permission model; deleting a connection revokes routing immediately, not on next boot.
- **AC-07** Orchestration integration: Maestro's capability registry (S8-01) consumes connection state, so an unavailable vendor is named as unavailable with an alternative offered rather than silently skipped.
- **AC-08** Browser session manager: one persistent profile per provider with isolated cookies, local storage, and browser state, so no provider can read another's session; connect, disconnect, logout, and clear-session operations; statuses `connected` / `login-required` / `session-expired` / `unavailable`, with expiry and login-required handled rather than surfaced as a dead pane. No password is ever collected, stored, or requested by Greeneek, and no authentication cookie is extracted, copied, or transferred into Greeneek's application or agent state.
- **AC-09** Manual browser UI: the provider opens in Greeneek's own browser surface with the session status and the connect/disconnect/logout/clear actions, and manual interaction stays available when automation is unavailable.
- **AC-10** Independent capability declaration: manual interaction and authorized automation are declared separately per provider (`BrowserAIProvider` descriptor), so a provider that supports only Manual Mode can never be asked to automate, and the request is refused by name rather than attempted and misreported.
- **AC-11** Permission-gated automation: Maestro and Modes reach a session only through a permission-controlled interface that never receives the raw profile or credential state; navigation, typing, submission, and reading visible responses require the user's approval wherever the action is sensitive or has an external consequence, reusing the existing approval model rather than a parallel one.
- **AC-12** Hard boundaries, enforced in code and tested: no CAPTCHA, MFA, anti-bot, or access-control bypass; no private or undocumented endpoint used to imitate an official integration; no claim of a capability the matrix does not record.
- **AC-13** Sequenced delivery, research first: per-provider terms and technical research and the capability matrix; architecture and ADRs; the `BrowserAIProvider` contract and capability model; the isolated session manager; Manual UI and authentication flow; authorized interaction and its permission model; Maestro and Modes integration; then security, integration, and end-to-end tests. Automation for one provider must not be assumed from another's result.

### 2026-11-04 — One-shot results reach the Lead as ordinary mailbox items, queued before the terminal edge
